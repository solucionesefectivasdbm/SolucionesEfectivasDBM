# Payment Amount Reversal Specification (new capability)

## Purpose

Defines the "revert amount" operation: an admin or registrador undoes the
registration of a payment's amounts (capital/interest), returning the installment
to the validated-unpaid state, with a LIFO guard, cascade and credit reopen.
Rejection `detail` strings are backend-owned Spanish UI copy; scenarios fix
semantic content, not exact wording. Endpoint path is a design decision.

Test tags: `[pytest]` backend-automatable; `[manual]` frontend, no runner.

## ADDED Requirements

### Requirement: Role Gate

Only `admin` and `registrador` MAY revert an amount. Any other role (including
`recaudador` and `gestor`) MUST receive HTTP 403 before any payment state is read.
The caller MAY revert any registered amount regardless of who registered it
(including their own). No `registrado_por_id` column or migration is introduced.

#### Scenario: Allowed roles `[pytest]`
- GIVEN a registered latest payment
- WHEN an `admin` (or a `registrador`) calls revert amount
- THEN the response is 2xx

#### Scenario: Forbidden roles `[pytest]`
- GIVEN a registered latest payment
- WHEN a `recaudador` or `gestor` calls revert amount
- THEN the response is 403 and nothing changes

### Requirement: Revertible Target

Only an installment with `pagado = True` MAY be reverted. Otherwise the endpoint
MUST reject with HTTP 4xx (422) and a plain-string `detail`, without modifying
state or writing an audit entry. A second call on an already-reverted payment
MUST be rejected, never a silent success.

#### Scenario: Unpaid installment `[pytest]`
- GIVEN an installment with `pagado = False`
- WHEN revert amount is called
- THEN the response is 422 stating there is no registered amount to revert

#### Scenario: Double call `[pytest]`
- GIVEN the latest registered payment
- WHEN revert amount is called twice in sequence
- THEN the first is 2xx, the second is 422, and only the first call's audit entries exist

### Requirement: LIFO Guard

Reversal MUST be blocked with a clear HTTP 4xx (422) while any later registered
payment exists for the same credit. "Later" is ordered by `fecha_pago_real`, then
the registration instant, then `id` as tiebreaker, and MUST NOT rely on `numero_cuota`.
The registration instant is `created_at` for a `no_programada` payment; for a scheduled
installment it is the `created_at` of its live scheduled successor (generated in the same
transaction), falling back to its own `updated_at` when it has none (closing payment),
because a scheduled installment's own `created_at` is its generation time, not its payment time.
Registered `no_programada` payments MUST count in this ordering. The rejection
message MUST tell the operator that later payments must be reverted first.

#### Scenario: Earlier payment blocked `[pytest]`
- GIVEN a credit with payments P1 then P2 both registered
- WHEN revert amount is called on P1
- THEN the response is 422 and nothing changes

#### Scenario: Latest payment allowed `[pytest]`
- GIVEN the same credit
- WHEN revert amount is called on P2
- THEN the response is 2xx, and a subsequent revert of P1 is also allowed

#### Scenario: No-programada counts as later `[pytest]`
- GIVEN a registered scheduled payment P1 and a later registered `no_programada` payment U
- WHEN revert amount is called on P1
- THEN the response is 422 until U is reverted

### Requirement: Installment Restore

On success the reverted installment MUST return to validated-unpaid: `pagado = False`,
`capital_pagado = 0`, `interes_pagado = 0`, `fecha_pago_real = None`,
`es_excedente_a = None`, while `validado_recaudador` and `tipo_validacion` are kept.
The installment MUST be registrable again afterwards.

A reverted `no_programada` payment is the exception: it was never validated, so it MUST
be soft-deleted (`deleted_at` set, together with its repartos) instead of being restored
to validated-unpaid.

#### Scenario: Restored state `[pytest]`
- GIVEN a registered latest payment that was validated
- WHEN it is reverted
- THEN the installment is validated, unpaid, with zero amounts and null `fecha_pago_real`
- AND registering it again succeeds

#### Scenario: No-programada soft-deleted `[pytest]`
- GIVEN a registered `no_programada` payment that is the latest of its credit
- WHEN it is reverted
- THEN the payment and its repartos have `deleted_at` set
- AND no unpaid validated installment is left in its place

### Requirement: Successor Installment Removal

The installment generated by registering the payment (N+1) MUST be soft-deleted
(`deleted_at` set) on revert. N+1 MUST be unpaid with zero amounts; if it is paid
or has any amount, the revert MUST be rejected with 4xx. Any check or deferral
already placed on N+1 is lost with it (accepted, documented). A payment that generated no successor
(e.g. `no_programada`, final installment) MUST revert without this step.

#### Scenario: Successor soft-deleted `[pytest]`
- GIVEN registered P with an unpaid, amount-free generated successor
- WHEN P is reverted
- THEN the successor has `deleted_at` set and the credit has exactly one unpaid installment (P)

#### Scenario: Successor has amounts `[pytest]`
- GIVEN registered P whose successor has `capital_pagado > 0` or `pagado = True`
- WHEN revert is called on P
- THEN the response is 422 and nothing changes

### Requirement: Credit Balance Recompute

Credit `saldo_capital`, `saldo_intereses` and carryover (arrastre) MUST be
recomputed from the schedule state after the revert, not by inverting stored
deltas and not by restoring values from `audit_log`. After reverting the latest
payment, credit balances MUST equal their values immediately before that payment
was registered (including after `abono_capital`, excedente-to-interests, and
floor-at-zero cases). `saldo_intereses` MUST be nonzero only under the existing
`cuota_fija` rule. The restored scheduled installment MUST keep its stored amounts
(registering a payment never changes them), so the current-installment recompute
MUST NOT be applied to it. When a `no_programada` payment is reverted, arrastre MUST
be re-derived via the existing current-installment recompute.

#### Scenario: Cuota fija round trip `[pytest]`
- GIVEN a cuota_fija credit with recorded balances B0, then a registered payment
- WHEN the payment is reverted
- THEN `saldo_capital` and `saldo_intereses` equal B0

#### Scenario: Abono capital round trip `[pytest]`
- GIVEN an `abono_capital` payment on a credit with balances B0
- WHEN it is reverted
- THEN `saldo_capital` equals B0 and `saldo_intereses` stays 0

#### Scenario: Excedente round trip `[pytest]`
- GIVEN a payment registered with an excedente applied to interests
- WHEN it is reverted
- THEN balances equal those before that payment and `es_excedente_a` is cleared

### Requirement: Credit Reopen

If the credit is closed (`activo = False`) because of the reverted payment, whether
by settled state or by regla 14 explicit closure, the revert MUST reopen it
(`activo = True`). For explicit closure, `saldo_intereses` MUST be recomputed from
the schedule state. A payment reverted on a still-open credit MUST NOT change
`activo`. The explicit-closure interest MUST be obtained by replaying every paid
payment of the credit except the reverted one, starting from the `cuota_fija` base
formula (0 for `abono_capital`), without reading `audit_log`.

#### Scenario: Settled credit reopens `[pytest]`
- GIVEN a credit closed by its last payment
- WHEN that payment is reverted
- THEN the credit is active again with a single unpaid, validated installment

#### Scenario: Explicit closure with pending interest reopens `[pytest]`
- GIVEN a credit closed via regla 14 with pending interest zeroed at closure
- WHEN the closing payment is reverted
- THEN the credit is active and `saldo_intereses` reflects the schedule, not zero

### Requirement: Optional Reason, Audit and Concurrency

The request MAY include a reason; it MUST NOT be required. Every successful revert
MUST be audited through `audit_service.registrar_*` helpers (never direct inserts
to `audit_log`), attributing the caller and recording changes to `pagado`, amounts,
`deleted_at` of the successor, credit balances/`activo` and the reason when given.
The credit row and affected payments MUST be locked with `SELECT ... FOR UPDATE`
for the request. Rejected calls MUST NOT modify state or write audit entries.

#### Scenario: Audit written `[pytest]`
- GIVEN a successful revert with reason "monto digitado mal"
- THEN audit entries attributed to the caller exist for `pagado` True to False and include the reason

#### Scenario: Reason omitted `[pytest]`
- WHEN revert is called without a reason
- THEN the response is 2xx

#### Scenario: Concurrent reverts serialize `[pytest]`
- GIVEN two simultaneous reverts of the same payment
- THEN exactly one succeeds and the other is rejected

### Requirement: Frontend Action

`authStore` MUST expose `canRevertirMonto` true only for `admin` and `registrador`.
`PagosPage` (weekly and daily views) MUST show a "Revertir monto" action only on
paid rows and only when `canRevertirMonto`, behind a confirmation with an optional
reason field. While the request is in flight the control MUST be disabled. Failures
MUST show backend `detail` verbatim (never the literal `Error`), and the list MUST
be refetched after success or a 4xx.

#### Scenario: Visibility `[manual]`
- GIVEN a paid row
- WHEN viewed by admin or registrador
- THEN "Revertir monto" is shown; for recaudador or gestor it is not

#### Scenario: Guard rejection surfaced `[manual]`
- GIVEN a paid row that is not the credit's latest registered payment
- WHEN the user confirms "Revertir monto"
- THEN the toast shows the backend LIFO message and the list refreshes

## Non-Goals

- Reverting out of order, full-cascade or edit-and-recompute reversal.
- `registrado_por_id` column; mandatory reason.
- Blocking on negative receptor balance.
- Changes to check validation or its reversal rules.
